# 16｜执行结果未知，为什么不能自动重试？

这是本仓库 ActionGate 的修复记录，不是分布式 exactly-once 的实现声明。

## HTTP 异常发生在执行边界的哪一侧？

用户批准终止慢查询。外部系统完成了动作，返回工单号时连接却断了。应用看到的是异常，不是外部系统的真实状态。

把卡片改回 ISSUED，看似方便用户重试，却重新开放了第二次写操作。HTTP 500 不能证明第一次没有执行，浏览器超时也不能回滚服务器的动作。

| 发生位置 | 状态处理 | 是否允许重新提交 |
| --- | --- | --- |
| 字段校验、授权、Handler 纯参数预检 | 尚未申领，不进入执行器 | 仅明确的参数错误允许修正 |
| 进入 Handler 后异常或缺少完整成功回执 | EXECUTION_UNKNOWN | 不允许直接重试 |
| 返回确定成功和非空工单号 | SUBMITTED | 不允许再次执行 |

## 批准对象必须承载真正要执行的参数

ActionGate 从签发快照还原字段，校验归属、类型、只读值和编辑范围。校验后的同一份不可变映射进入 ApprovedCardSubmission；其构造器不对外公开，Handler 不再接收原始 HTTP DTO。

运维 Handler 将 max_pool_size、remark、目标、服务、幂等键和批准人的身份传到 OpsActionParam。不能让用户批准容量 120，执行器却收不到该参数。

真实操作人来自服务端 Principal，权限由宿主提供 ActionAuthorizer。固定的 SRE-Oncall 字符串或 X-User-Id 请求头不是认证。没有授权实现就拒绝；本机 Mock 演示使用另一条显式配置路径。

## 存储与执行要共同维护边界

单机存储的签发、申领、驱逐共用短临界区，不在锁内调用外部服务。查询返回副本，签发版本使用 UUID：校验后原提案被清理并重新签发，同 actionId 的新记录也不能接受旧批准。

容量满时拒绝新提案，不为腾空间删除执行中或保留期内的记录。EXECUTION_UNKNOWN 不因 TTL 自动删除，否则等待过期又会打开未知副作用。这也意味着未知结果可能占满容量，需要运维核查，而不是假装自动恢复。

## 当前限制

记录仍在单个 JVM。生产适配器必须持久化审批/执行记录，把幂等键传给真正产生副作用的系统，并提供结果核查、人工处置与跨节点一致性。

批准类型是可信 Java 扩展之间的契约，不是阻止恶意同进程代码的沙箱。不能声称所有普通 Java 执行路径都获得不可绕过的系统级隔离。

对应回归：ActionGateTest、CardRegistryTest、CardInteractionControllerTest、OpsActionCardSubmitHandlerTest。
