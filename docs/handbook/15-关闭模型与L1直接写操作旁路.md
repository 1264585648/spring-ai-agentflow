# 关闭模型与 L1 的直接写操作旁路

> 日期：2026-10-13
>
> 范围：关闭已知的 `OpsActionTool.executeEmergencyAction` 模型调用与 L1 直通入口，保留查询和模拟卡片流程。本次不实现完整 ActionGate，也不代表真实写操作已经可以安全上线。
>
> 验证状态：已做改动文件的 Java 语法解析和差异检查；Maven 编译、JUnit 测试与完整应用联调尚未执行。本次编辑环境没有 Maven，也无法解析 GitHub 主机取得完整 checkout。下文测试是已加入仓库的回归用例，不是测试通过记录。

## 卡片确认之外，还有两条路径

修改前，`TroubleshootSubAgent` 同时向 `AgentChatClientFactory` 传入日志、数据库与运维执行工具。模型可以通过 `OpsActionTool.executeEmergencyAction()` 调用 `OpsActionPort.executeAction()`，不需要先提交卡片。

另一方面，`L1ToolCatalog` 会扫描 Spring Bean 上的 `@Tool` 方法。即使从模型的工具列表移除写工具，只要写方法仍有注解，指向 `opsActionTool.executeEmergencyAction` 的 L1 规则仍可能直通执行。

因此，这一步需要同时移除两个入口：模型的工具挂载，以及 L1 所依赖的写方法注解。没有在通用内核里添加运维业务名称黑名单，也没有禁用整个工具目录。

## 这次具体改了什么

`TroubleshootSubAgent` 不再导入、注入或挂载 `OpsActionTool`。模型侧仍可使用原来的两个查询工具：

```java
ChatClient agentClient = chatClientFactory.createClient(
        targetAgentCode,
        logQueryTool,
        databaseDiagnoseTool
);
```

`OpsActionTool.executeEmergencyAction()` 去掉 `@Tool` 注解，并删除对应 import。这个类暂时保留原有名称和普通 Java 调用接口，避免把关闭暴露入口扩大为执行能力重构。方法本身没有鉴权或审批能力，普通 Java 调用仍然不是安全的审批入口。

`OpsActionPort`、`OpsActionCardSubmitHandler`、`CardRegistry` 和卡片模型未被删除。原有模拟卡片演示路径继续保留；本次没有新增真实运维适配器，也没有实现通用的生产写禁用开关。

原有三个测试类中直接构造 `TroubleshootSubAgent` 的位置同步移除了写工具参数，流式测试的工厂 stub 改为两个查询工具参数。既有功能断言保留，不用删除测试来适配变更。

## 测试检查的是实际边界，而不只是传参

新增 `DirectWriteToolBoundaryTest`，使用小型 `AnnotationConfigApplicationContext` 和真实的 `AgentChatClientFactory` / `ChatClient`。模型使用 Mock，查询使用现有 Mock 适配器，写端口使用 Mock 适配器的 spy，不连接真实运维系统。

| 用例 | 应验证的行为 |
| --- | --- |
| 模型侧工具定义，覆盖四个受支持的排障角色 | 捕获真正传给 `ChatModel.stream()` 的 `Prompt`，工具定义只有 `queryServiceLogs` 和 `diagnoseDatabase`；写端口没有调用 |
| 查询工具的正向对照 | 通过捕获到的真实 `ToolCallback` 调用 Mock 查询能力，仍能获得日志和数据库诊断内容 |
| L1 写入口拒绝 | 在上下文中仍注册真实 `OpsActionTool` Bean，使用实际扫描生成的目录；旧的写目标引用被拒绝，写端口没有调用 |
| L1 查询直通 | 日志、数据库查询仍在目录中并可执行，不以禁用所有工具来获得安全测试通过 |
| 模拟卡片流程 | 下发卡片时不执行；签发后提交到 Controller，Mock 端口执行并返回工单；同一卡片重复提交返回冲突，不重复调用端口 |

模型侧测试还要求捕获到模型调用和约定的模型输出，避免 ChatClient 装配异常后进入演示兜底，却误让测试通过。

卡片测试显式构造 Handler 并注入 Mock Port，覆盖既有模拟提交路径；它不是整个 Spring Boot 应用的装配测试，不证明 Handler 当前的多构造器装配问题已经修复。

在具备项目构建环境的工作区运行：

```bash
mvn -B -Dtest=DirectWriteToolBoundaryTest,TroubleshootSubAgentTest,AgentPipelineServiceImplTest,MultiTurnPipelineIntegrationTest,CapabilityToolsTest,OpsActionCardSubmitHandlerTest,L1ToolDispatcherAllowlistTest test
```

这些用例不需要真实模型 Key 或真实运维服务；Maven 仍需能够解析项目依赖。合并前应完成上述回归，并根据项目环境运行完整测试。语法解析不检查第三方 API 类型兼容性，不能替代编译和 JUnit。

## 对已有接入的影响

部署需要重启应用，让工具目录重新扫描。已有 L1 规则若仍指向 `opsActionTool.executeEmergencyAction`，升级后会被拒绝；本次不自动修改或删除用户的规则数据，也不自动将它转换成已经批准的动作。管理员应停用这些旧规则，等待后续提案入口。

直接构造 `TroubleshootSubAgent` 的接入代码需要同步移除 `OpsActionTool` 参数；本仓库已读取到的三个测试类对应调用点已调整。Spring 管理的实例则按新的构造器依赖装配。

## 还没有解决什么

本次只是针对已知工具的暴露面收缩，不是所有写操作的统一运行时防线。未来新增写工具、程序化工具注册、业务代码直接调用 Port，都不能靠这次移除注解自动获得审批保护。

后续仍需基于现有 `CardRegistry` 补齐可信身份、卡片类型绑定、服务端参数重建与执行幂等，再抽出最小的 ActionGate。当前演示卡片仍包含固定示例目标；在这些问题完成前，只使用模拟写适配器，不应接入真实 Kill、扩容或重启操作。
