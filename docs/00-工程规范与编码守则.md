# 工程规范与编码守则 (Engineering Standards)

> **文档定位**：全工程最高编码与架构质量准绳。所有功能开发、重构、组件抽取均需严格遵守本文档所列规范。  
> **维护原则**：随日常开发与交流持续固化、动态追加，先定准则再动代码。

## 规范详则说明

### RULE-01：实体与模型规范（Lombok @Data 准则）
1. **强制使用 `@Data`**：
   - 所有数据传输对象（DTO）、请求入参、实体类（Entity）、值对象（VO）必须引入并标注 Lombok `@Data`（配合 `@NoArgsConstructor`、`@AllArgsConstructor`）；
   - **禁止** 在类中手写冗长、无业务逻辑的 getter/setter 方法，保持类文件干净清爽，聚焦字段定义与业务注解。
2. **特殊场景约定**：
   - 若某个 setter 存在非标准转换逻辑（例如设置表达式时同步预编译正则、敏感字段解密等），允许显式保留该特定方法，其余通用属性仍由 Lombok 生成。

---

### RULE-02：数据库与持久层规范（物理脚本单一事实标准）
1. **配置红线**：
   - `application.yml` 中 JPA 的 `hibernate.ddl-auto` 必须显式声明为 `none`，**绝对禁止**设为 `update` 或 `create`；
2. **唯一物理契约**：
   - 所有新表创建、历史表字段增删、索引调整、演示种子数据，一律维护在根目录的 `sql/init_schema.sql`；
   - 开源项目使用者必须仅凭执行该 SQL 脚本即可完成所有环境初始化。

---

### RULE-03：并发与线程池隔离规范（舱壁隔离原则 Bulkhead）
1. **禁止默认无界池**：
   - **严禁** 直接调用 `ForkJoinPool.commonPool()`、`CompletableFuture.runAsync(task)`（无指定 executor 参数）；
   - **严禁** 使用 `Executors.newCachedThreadPool()` 等无界队列线程池。
2. **专用舱壁池划分**：
   - 核心通信调度任务必须提交至 `agentPipelineExecutor`（有界队列 + CallerRunsPolicy 自然背压）；
   - 旁路低优先级任务（推荐追问、会话总结、异步命中日志）必须提交至 `agentAsyncPostExecutor`（DiscardOldestPolicy，绝不阻塞主流程）。
3. **命名可追踪**：
   - 所有线程池必须显式指定 `ThreadNamePrefix`，便于 `jstack` 线程堆栈分析与全链路排错。

---

### RULE-04：微内核边界红线规范（插座与插头哲学）
1. **框架中立性**：
   - 核心骨架（Core / Kernel）代码中不得出现具体行业或特定业务系统的硬编码字段；
2. **SPI 插件外挂**：
   - 卡片确认提交、SOP 工作流落地必须通过 `CardSubmitHandler`（SPI）由外部接入方自由实现，骨架仅提供 `@Order` 最低优先级的默认 Mock 兜底。

---

### RULE-05：流式通信契约规范（SSE 8 类事件流）
1. **统一包装对象**：
   - 消息下发必须封装为 `SsePacket<T>`；
2. **状态流转严格受控**：
   - 客户端只能接收到 8 种明确契约事件：`thinking`（推理链）、`message`（文字回答）、`progress`（进度）、`interactive_card`（交互卡片）、`recommend_questions`（推荐追问）、`conversation_title`（会话标题）、`done`（回合结束）、`error`（异常）。
3. **契约先行**：
   - 新增或修改事件、字段、接口路径，必须先修订 [03-前后端接口与SSE协议契约](./03-前后端接口与SSE协议契约.md)，再同步修改 `SseEventType` 与 `frontend/src/types/chat.ts`。

---


### RULE-06：多智能体动态管理与生命周期守则（增减与治理防线）
1. **分层治理边界**：
   - **骨架管道类 Agent**（如 `QUERY_REWRITER`、`MASTER_AGENT`）：标记为 `is_system_core = 1`，数据库只管 Prompt、模型和采样超参，**严禁增删节点结构**；
   - **业务领域 Sub-Agent**（如 `GITHUB_ISSUE_AGENT`、`GITHUB_PR_AGENT`、`GITHUB_RELEASE_AGENT` 等）：支持后台动态新增、修改人设及挂载工具池能力。
2. **物理删除红线（减要慎重）**：
   - **严禁**在数据库或管理后台对 Agent 执行物理删除（`DELETE`），必须通过状态机流转：`DRAFT`（草稿）➔ `ONLINE`（在线）➔ `DEPRECATED`（下线排空中）➔ `OFFLINE`（已下线）。
3. **下线前置依赖审计**：
   - 执行下线或停用前，系统必须前置检查 L1 规则表（`sys_rule_definition.target_ref`）或多步工作流链是否存在硬引用，存在依赖时强行阻断。
4. **零停机无锁热重载**：
   - 智能体元数据必须采用无锁内存快照（`AtomicReference`）提供读服务，配置变更后通过事件总线通知集群平滑替换快照。

---

### RULE-07：日志与追踪规范（Lombok @Slf4j 准则）
1. **强制使用注解声明**：
   - 全工程所有需要打印日志的组件类（Controller、Service、Component、Config、Dispatcher、SPI Handler 等），一律使用 Lombok `@Slf4j` 标注在类级别；
   - 统一使用注解放出的默认变量名 `log`，严禁自定义 Logger 变量名称。
2. **严禁手动创建 Logger 实例**：
   - **绝对禁止** 在类中手写 `private static final Logger log = LoggerFactory.getLogger(Xxx.class);` 或 `Logger.getLogger(...)` 这类冗长样板代码；
   - 移除类中无用的 `org.slf4j.Logger` 与 `org.slf4j.LoggerFactory` 导入包，保持代码极致清爽。

---

### RULE-08：内核扩展点优先规范
1. **先定契约，再填实现**：
   - 意图解析、业务 Agent、治理钩子等新能力，必须先以 [07-内核架构设计与演进路线](./07-内核架构设计与演进路线.md) 中定义的扩展点接口（`IntentResolver`、`SubAgent`、`AgentHook`、`CardSubmitHandler` 等）落在内核，再以 Spring Bean 形式提供实现；
2. **流水线零业务分支**：
   - 流水线编排代码只负责按扩展点调度，禁止追加针对某个规则类型、某个业务场景的 if/else 分支；
3. **默认实现开箱即用**：
   - 每个扩展点都必须提供无外部依赖的默认实现（Mock / 内存版），保证开源使用者无需外部系统即可运行。
4. **业务编码不进内核**：
   - 内核代码（含 `AgentType` 等枚举）只允许出现骨架类智能体编码（如 `QUERY_REWRITER`、`MASTER_AGENT`）；业务 Sub-Agent 编码、业务工具与业务卡片只存在于注册中心数据与业务模块中，这是 RULE-06“业务类动态增减”的前提。

---

### RULE-09：配置与凭证安全规范
1. **禁止提交真实凭证**：
   - `application.yml` 等任何入库文件中不得出现真实密码、API Key、Token；
   - 占位符不得携带真实默认值（如 `${DB_PASSWORD:真实密码}`），默认值只允许空值或 `localhost` 级别的示例值；
2. **禁止提交内部地址**：
   - 公司内部域名、内网数据库地址、配置中心地址不得出现在开源仓库中，统一通过环境变量或本地未入库的 `application-local.yml` 注入；
3. **泄露处置**：
   - 一旦发现凭证已入库，必须先轮换凭证，再清理文件与 Git 历史。

---

### RULE-10：组件正交与原子能力一级公民守则（Composable Capabilities）
1. **严禁烟囱式垂直捆绑**：
   - 横向通用底层技术能力（如服务日志检索、数据库运行指标、运维处置执行等）必须作为系统的一级原子能力（位于 `capability.*`）独立定义与演进，**绝对严禁**将其作为私有附属物绑死在具体垂直业务场景（如 `troubleshoot`）内；
2. **能力高内聚与自包含闭环**：
   - 每个原子能力必须自包含其专属的标准端口（Port SPI）、领域模型（Model/DTO）、开箱即用的仿真适配器（Mock Adapter）和专属大模型工具（Tool），自成完整技术闭环；
3. **最小特权原则工具挂载**：
   - 智能体只能挂载其职责范围内的原子能力工具（如 `LOG_DIAGNOSE_AGENT` 仅挂载 `LogQueryTool`，`DB_DIAGNOSE_AGENT` 仅挂载 `DatabaseDiagnoseTool`），严禁跨能力打包大一统工具造成权限越界和 Token 膨胀；
4. **场景仅负责协同编排（Orchestration）**：
   - 业务场景（`scenario.*`）是一级原子能力的消费者与编排者。场景只负责多智能体任务拆解、提示词装配与交互卡片协同，场景本身不得持有底层数据查询端口。

---

### RULE-11：微内核纯净性与 SubAgent 场景编排插件化守则（Zero-Domain Microkernel & SubAgent Plugin）
1. **微内核零业务依赖（Zero Domain Knowledge in Core）**：
   - `core.*`（尤其是 `core.pipeline`、`core.routing`、`core.agent`）必须保持 100% 纯净与业务概念无关；
   - 严禁在内核中出现任何特定业务场景词汇、特定错误代码（如 `504`、`order-service`、`HikariCP`、`trx_10423`）、硬编码提示词模板或特定业务卡片装配逻辑；
2. **SubAgent 标准插件化规范**：
   - 所有具体业务场景（包括运维故障排障、日常健康巡检、发布上线验证等）必须作为 `SubAgent` SPI 的具体实现类，统一放置在 `scenario.<scene>` 包下；
   - `SubAgent` 必须声明其支持的智能体唯一编码（对应 `sys_agent_definition.agent_code`），通过统一的 `execute(AgentContext ctx, RouteStep step)` 完成业务推理、大模型交互、流式回传与交互卡片下发；
3. **上下文统一载体（AgentContext）**：
   - 会话请求在接入层转换为 `AgentContext`，包含 `sessionId`, `turnId`, `query`, `attributes` 以及统一事件出口 `AgentEventSink`，内核与场景插件之间仅通过上下文对象进行数据交换；
4. **内核动态发现与优雅兜底**：
   - `core.pipeline` 通过 Spring 容器自动收集所有 `SubAgent` 插件实例，按路由结果派发。当未匹配到专业场景插件时，自动降级委托给通用兜底智能体（`GeneralChatAgent`），保障内核执行永不悬挂。
