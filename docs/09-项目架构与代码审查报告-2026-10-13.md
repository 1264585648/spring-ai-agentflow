## 1. 结论与最优先事项

### 1.1 总体判断

**保留现有设计，不建议推倒重来；但应暂停扩展新 Agent，先完成一轮安全边界、依赖装配和功能链路修复。**

项目已经形成有价值的模块化基础：意图解析责任链、统一决议模型、SubAgent 扩展点、Capability Port、卡片状态机、独立事件出口、元数据快照及前端流式工作台。这些不是只有文档的空设计。

但当前更准确的定位是：**带插件接口的单体原型，正在向通用框架演进**。不能把“有接口”“有实现”“演示能返回内容”直接等同于“功能闭环已经正确”“已经适合接真实写操作”或“可作为通用依赖交付”。主要依据见 [Pipeline][S01]、[排障场景][S02]、[路由器][S16]、[项目构建文件][S20]。

影响现阶段可靠性的核心问题不是抽象层数不够，而是：

- 文档中的人工确认规则，没有成为所有写操作的强制执行边界。
- 部分组件的真实 Spring 装配与单元测试中的手动构造不一致。
- 历史、改写结果和知识提示已经产生，但没有完整进入最终模型输入。
- 回合、步骤、卡片与真实执行结果之间缺少足够强的关联。
- 演示兜底与生产行为没有明确分离。

### 1.2 应该最先改什么

**第一优先：堵住“未经可信确认就执行”的路径。** 对应 F01、F02、F05、F11。移除模型可直接调用的写工具；卡片类型、目标、身份和执行参数必须由服务端签发记录及认证上下文决定；没有可靠目标就不生成可执行卡片。真实业务适配器接入必须以这些修复为前提。

**第二优先：修复装配，并建立能证明真实装配行为的测试。** 对应 F03、F17。生产组件不再依靠无参构造器填入 `null` 或自行创建 Mock。先证明应用实际使用了预期依赖，再评估功能效果。L2 装配修复与向量空间修复必须配套，不应立即启用来源不一致的索引。

**第三优先：把一条对话主链路做正确。** 对应 F04、F06、F07、F08。确保最终模型输入包含必要上下文，检索数据来源一致，HTTP 与 SSE 的失败有终态，旧回合事件不会污染新回合。

**不建议最先做的事情：**拆多个 Maven 模块、引入复杂 DAG 引擎、增加更多专家、增加新的中间件。否则只是把已有问题搬进更复杂的结构。

### 1.3 不采用“完成度百分比”

本报告不提供未经验收定义支持的完成度评分。每项能力分别讨论实现存在性、调用链是否接通、验证证据和运行限制。“接口存在”不能替代验收，“未完成的规划”也不自动等于代码缺陷。

## 3. 整体架构与能力现状

### 3.1 当前主链路

以下是对实际调用关系的概括，不是目标架构图：

```text
React ChatDrawer
  ├─ GET /api/v1/chat/connect ──> SSE 连接管理
  ├─ POST /api/v1/chat/ask ─────> ChatController
  │                               └─ AgentPipelineServiceImpl
  │                                  ├─ 读取历史 / 查询改写
  │                                  ├─ IntentResolver 责任链
  │                                  │   ├─ L1 规则
  │                                  │   ├─ L2 检索（存在装配缺陷）
  │                                  │   └─ L3 路由
  │                                  ├─ DirectReply / ToolCall / Route
  │                                  └─ SubAgent
  │                                      ├─ GeneralChatAgent
  │                                      └─ TroubleshootSubAgent
  │                                           ├─ ChatClient + Tools
  │                                           └─ 处置卡片
  │
  └─ POST /api/v1/card/submit ──> CardRegistry 校验
                                  └─ CardSubmitHandler
                                      └─ OpsActionPort

额外存在的旁路：模型调用 OpsActionTool ──> OpsActionPort
该旁路不要求经过卡片确认。
```

证据：[Pipeline][S01]、[排障场景][S02]、[操作工具][S03]、[卡片入口][S05]、[前端客户端][S13]。

### 3.2 值得保留的设计

| 设计 | 价值 | 需要守住的边界 |
| --- | --- | --- |
| `IntentResolver` + `Resolution` | 将识别决策与具体执行分离，容纳直答、工具和路由 | 不在 Pipeline 继续堆业务关键词 |
| `SubAgent` | 已有真实的场景实现入口 | 接口存在不等于步骤输入输出已完整 |
| Capability 的 Port / Tool / Mock | 为外部系统适配保留替换位置 | Tool 不应天然获得真实写权限；Mock 不应隐式进入生产 |
| `CardRegistry` | 已有签发记录、状态竞争、只读字段比对 | 继续补可信身份、类型绑定、参数重建与执行幂等 |
| 快照与热重载 | 适合将管理写入与运行时读取分开 | 单机原子切换不等于跨节点强一致 |
| `AgentChatClientFactory` 的 Builder 克隆 | 避免不同 Agent 直接互相修改默认提示词 | 仍需真正应用模型参数和工具权限 |
| L1 `@Tool` 方法目录 | 比任意 Bean 方法反射执行更可控 | 注解白名单不是用户授权，也不是人工确认 |
| SSE 按连接实例精确移除 | 避免旧连接回调误删新连接 | 仍需回合关联、准入和取消语义 |

对应实现见 [S01][S01]、[S04][S04]、[S15][S15]、[S27][S27]、[S28][S28]、[S29][S29]。

## 5. 详细问题与修复要求

### F01｜人工确认没有成为写操作的唯一执行入口

**定位：**[TroubleshootSubAgent.execute()][S02]、[OpsActionTool.executeEmergencyAction()][S03]。

排障场景创建客户端时同时挂载日志、数据库和运维操作工具：

```java
chatClientFactory.createClient(targetAgentCode,
        logQueryTool, databaseDiagnoseTool, opsActionTool);
```

`OpsActionTool` 的 `@Tool` 方法直接调用 `opsActionPort.executeAction(param)`，不是只生成操作建议。因此存在不经过 CardRegistry、Controller 和人工确认的执行路径。日志专家和数据库专家也获得了相同工具集合，与工程规范的最小权限要求不符。

**影响边界：**当前默认适配器是 Mock，不能据此断言已经发生真实运维操作；但只要将端口替换为真实实现，旁路便可能产生真实副作用。

**修复要求：**模型侧只暴露查询、诊断和生成草案的工具。真实写操作由服务端应用服务统一执行，该服务校验可信身份、审批记录、目标资源、动作范围和幂等键。Prompt 中的“先征求同意”不是权限控制。也要检查 L1 工具直通，避免保留第二条绕过路径。

**验收：**让可控假模型主动请求写工具，真实执行端口的调用次数必须为零；日志专家不能获得数据库写操作或运维执行工具；确认后的合法操作只能通过受控入口执行。

### F02｜卡片归属、类型及实际执行参数没有完全绑定

**定位：**[InMemoryCardRegistry.claim()/validate()][S04]、[CardInteractionController.submitCard()][S05]、[OpsActionCardSubmitHandler.handleSubmit()][S07]。

归属比较仅在请求和记录的 `sessionId` 都非空时发生。持有有效 `actionId` 且表单满足其他校验的请求，可以通过省略会话跳过这次比对。Controller 只强制检查 `actionId`，处理器又通过 `request.getCardType()` 选择，而不是通过签发记录中的类型选择。校验后仍把原始请求交给 Handler。

同时，表单校验主要比较只读值及必填项，没有完整约束字段类型、取值范围、额外字段；Handler 还能从表单读取操作人。

**修复要求：**签发记录保存可信 owner、会话、回合、卡片类型及不可变操作草案。请求原则上只提交 `actionId` 和允许编辑的字段；服务端按记录恢复类型和只读值，仅合并白名单内的可编辑字段，再形成新的执行请求。身份来自认证上下文，不来自表单。空身份、跨用户和跨会话必须拒绝。

**注意：**只加 `@NotBlank(sessionId)` 仍不是鉴权；客户端能填写一个会话字符串，不代表它拥有该会话。

**验收：**缺失身份、空会话、跨会话、替换卡片类型、增加未授权字段、超范围参数、只读篡改都不能执行；校验失败不能让卡片永久卡在 `SUBMITTING`。

### F03｜兼容性构造器导致静默装配错误

**定位：**[L2VectorResolver 构造器][S06]、[OpsActionCardSubmitHandler 构造器][S07]。

两类都有多个构造器，且没有指定注入构造器：

```java
public L2VectorResolver() {
    this(null, null);
}

public OpsActionCardSubmitHandler() {
    this(new MockOpsActionAdapter());
}
```

依据 Spring 的默认构造器选择规则，默认组件扫描路径会使用可用的默认构造器。前者导致 `resolve()` 因依赖为空直接放行；后者绕过容器中的端口 Bean，使用自行创建的 Mock。此处属于源码事实与框架规则推导，尚未在本环境实际启动容器验证。官方依据见 [E01][E01]。

**修复要求：**生产组件保留一个明确的必需依赖构造器；确需多个时标明注入入口。测试通过显式的测试配置提供假依赖，不在生产组件中塞入空对象或私建 Mock。缺少关键生产能力应明确失败，不能模拟成功。

**特别风险：**卡片路径继续使用私建 Mock，而模型工具路径使用容器中的真实端口时，两条路径会表现不一致。不能只替换 Adapter 就认为人工确认流程已经真实接通。

**验收：**从真实 Spring 容器取得组件，以可记录调用的端口/Embedding Bean 验证实际调用；没有执行路径回落到隐式 Mock。修复 L2 装配后，应先验证 F06，再启用已有索引。

### F04｜多轮记忆、改写结果和 L2 知识没有完整进入最终回答

**定位：**[Pipeline.process()][S01]、[GeneralChatAgent.execute()][S08]、[TroubleshootSubAgent.execute()][S02]、[L2VectorResolver.resolve()][S06]。

Pipeline 读取历史并设置 `effectiveQuery`，L2 中置信度命中写入 `L2_HINT_ANSWER`。但通用 Agent 仍使用 `context.getQuery()` 直接构造用户消息；排障 Agent 也使用原始问题和步骤参数，未加入历史消息或 L2 标准答案。

可能出现“路由已经知道‘它’指什么，最终回答模型却没有得到足够上下文”的断层。排障步骤参数有时能补回服务名，但不能替代完整的上下文输入契约。

**修复要求：**统一模型输入组装。明确区分原始问题、用于路由的有效问题、有限窗口历史、检索资料和步骤输入。可以继续采用双轨设计：路由使用改写问题，生成保留原始问题与历史；也可以使用有效问题加必要历史。关键不是机械替换字符串，而是最终模型确实得到任务所需的信息。

知识资料应以明确的数据区块加入 Prompt，不把检索到的文本提升为系统指令。另需统一窗口单位：`MAX_HISTORY_ROUNDS` 传给 `getRecentMessages()`，而内存实现按消息条数截取，名称与实际计数语义应一致，见 [S17][S17]。

**验收：**捕获最终模型请求，验证指代、历史中的约束、L2 标准答案及引用标识被正确传递；不能只断言 Context 有字段或前端收到“改写完成”。

### F05｜固定处置目标与诊断证据脱节

**定位：**[TroubleshootSubAgent.execute()/buildFallbackExpertReply()][S02]、[OpsActionCardSubmitHandler.handleSubmit()][S07]。

正常回答和异常兜底之后，场景都会创建固定动作与固定目标的卡片：`Kill阻塞慢查询并临时扩容连接池`、`trx_10423`；缺少服务名时默认 `order-service`。Handler 也有相同的兜底目标。

**影响：**人工点击只能证明用户确认了显示的内容，不能证明该内容与真实诊断一致。纯咨询、缺少服务名、不同故障原因，都不应自然导向相同的可执行处置。

**修复要求：**由结构化 `ActionProposal` 生成卡片，包含实际资源、动作、风险、证据和参数。没有明确目标时追问或只给建议；不使用默认服务或默认事务填补缺失目标。生产模型异常时不伪造已完成诊断的事实；演示数据必须显式标为模拟。

**验收：**纯咨询不产生可执行卡片；目标未知时不执行；服务 A 的诊断不能生成服务 B 的操作；模型失败不自动生成固定真实目标的处置卡片。

### F06｜Embedding 失败时的假向量可能污染索引语义

**定位：**[DefaultVectorEmbeddingService.embed()][S09]、[L2FaqAdminController.createFaq()][S10]、[VectorSnapshot.searchTop1()/searchTopK()][S11]。

真实 Embedding 失败时自动返回本地 MD5、字符与 N-Gram 投影向量。FAQ 入库却固定写入 `text-embedding-3-small` 标识；检索只比较维度，没有验证向量来源及模型空间。

**根因：**相同维度不代表相同坐标空间。问题不在于 MD5 是否适合加密，而在于本地投影与真实模型 Embedding 不能直接作有意义的跨空间比较。当前代码存在产生混合来源的条件，但本报告没有检查实际数据库是否已经存在这类数据。

**修复要求：**Mock Embedding 仅在显式 demo/test 配置启用。生产调用失败时，知识入库应失败或保持待处理状态；查询可明确跳过 L2，但不能制造成功向量。记录真实模型、维度、预处理/空间版本，入库和查询同时校验。来源不明的旧向量隔离后重建。

`0.70`、`0.88` 是当前实现阈值，不是普适准确率保证。应用真实问答样本校准直答与路由阈值，尤其测试“措辞相近但操作目标相反”的问题。

**验收：**模型故障不会发布假向量；同维不同空间数据不能参与匹配；换模型必须执行受控迁移；L2 直答效果有样本集验证。

### F07｜SSE 没有贯穿回合标识

**定位：**[Pipeline.process()][S01]、[SsePacket][S14]、[ChatDrawer 的事件处理][S12]、[卡片提交后的 SSE 回执][S05]。

Pipeline 创建了 `turnId`，但当前统一事件对象只有 `event/data/timestamp`，没有将回合标识贯穿到客户端。前端收到文本、思考和卡片时，主要更新最后一条助手消息。

**触发场景：**用户开始新问题后再提交旧卡片，旧卡片的普通 message 回执可能被追加进新回答。前端单个 `isStreaming` 不能防住多客户端、旧连接重连及异步旧事件。

**修复要求：**定义 `/ask` 接受响应与 SSE 事件共同使用的 `turnId`，卡片也保存所属回合。前端按回合更新消息。可增加 `stepId/actionId/sequence`；协议扩展必须先更新 `03`，再同步 Java 与 TypeScript 类型。还要处理首个事件先于 HTTP 接受响应到达的竞态，不能只在响应后才建立唯一映射。

短期允许服务端限制同会话一个活动回合，或者明确排队，不必立即支持任意并行回合。

**验收：**旧事件不会进入新回合；重复终态和重复事件不破坏状态；多客户端并发请求有明确的拒绝、排队或独立回合行为。

### F08｜HTTP 失败与 SSE 连接状态未形成完整闭环

**定位：**[sseClient.sendQuestion()/connect()][S13]、[ChatDrawer.handleSendMessage()][S12]。

`sendQuestion()` 直接返回 `res.json()`，没有检查 HTTP 状态；调用方也没有检查返回业务码。错误 JSON 可能被当成成功接受，页面只等待一个不会到来的 SSE 终态。连接建立也没有明确的就绪确认与发送准入。

**修复要求：**统一请求处理，识别 HTTP 非成功状态、非 JSON 响应、业务错误及超时。将连接状态与回合状态分开；连接未就绪时禁发或排队；请求失败必须结束当前回合并保留可重试入口。区分服务端业务 error 事件和 EventSource 的传输错误。

**验收：**400/401/403/429/500、错误 JSON、代理 HTML 错误页、连接未就绪及断线都不会永久显示生成中；恢复行为不把旧任务当成新任务继续显示。

### F09｜后台配置不等于实际运行配置

**定位：**[AgentChatClientFactory.createClient()][S15]、[AgentDefinition][S30]。

Agent 元数据包括模型名称、温度、挂载工具等字段；当前客户端工厂主要使用 System Prompt，以及调用方显式传入的工具对象，没有完整把这些元数据转换为有效运行配置。

**影响：**管理员可以看到或修改某项配置，但运行行为未必变化。工具元数据尤其不能只作为展示信息，实际权限需要落到调用集合及服务端校验。

**修复要求：**增加明确的有效运行配置转换层，校验模型与参数、按权限解析工具，再创建客户端。未实现的字段在管理端标为暂不生效。不要为此重造一套模型调用框架，也不要简单让管理员输入任意 Bean 名来扩大执行范围。

**验收：**修改模型/参数后可在假模型接收到的请求中验证变化；Agent A 不能获得 Agent B 的工具；未知模型或工具配置明确拒绝；日志可追踪本回合采用的配置版本。

### F10｜复合任务目前更接近顺序调用，而非结果依赖协作

**定位：**[MasterAgentRouter.planLogAndDbComposite()][S16]、[Pipeline.executeRoute()][S01]、[TroubleshootSubAgent][S02]、[ChatDrawer][S12]。

两步计划使用同一组输入参数。第二步描述要求“结合 Step 1 日志异常”，但没有明确接收第一步的结构化结果。SubAgent 执行接口也没有形成标准的步骤结果传递。同时，两步可能各发一张卡片，而每条前端消息只保存一个 `interactiveCard`，后到卡片覆盖前者。

**修复要求：**先定义最小的 `StepResult`，包含步骤状态、结构化结果、证据、错误分类及可选操作草案。后续步骤明确引用前序结果；失败时明确停止、继续或降级。多卡片可以采用按 `actionId` 管理的集合，也可以规定场景汇总后只发一张最终卡片，二者择一并写入契约。

**验收：**第二步实际收到第一步结果；第一步失败后的策略可测试；多张卡片不会静默覆盖；不执行重复或互相矛盾的处置。

### F11｜执行结果和幂等语义不可靠

**定位：**[OpsActionCardSubmitHandler.handleSubmit()][S07]、[CardInteractionController.submitCard()][S05]、[InMemoryCardRegistry.fail()/complete()][S04]。

Handler 获取端口结果后直接返回 `CardSubmitResult.ok(...)`，没有根据业务失败状态分支处理；空结果还可能导致异常。Controller 对执行异常及失败结果通常释放回可重试状态，无法区别“外部未执行”与“外部已成功但响应丢失”。

**影响边界：**内存状态锁可以防止同一个实例内的部分重复点击，却不能保证外部系统只执行一次，不能跨重启和多节点提供同等保证。

**修复要求：**区分成功、确定失败、结果未知。使用 `actionId` 或绑定的执行标识作为结构化幂等键传到业务端口，而不是只把它写进 reason 文本。结果未知时先查执行状态，不盲目重试。真实写操作需要持久化执行记录；执行状态与 UI 回执分离，通知失败不能触发再次执行。

**验收：**端口返回失败时前端不能显示成功；外部已完成但调用超时后，重试不产生第二次副作用；服务重启后仍能查询同一执行结果。

### F12｜包分层尚未成为稳定的内核依赖边界

**定位：**[Pipeline 的 imports 与构造依赖][S01]、[L2VectorRegistry][S27]、[MasterAgentRouter][S16]。

Pipeline 直接接受 `web.dto.ChatRequest`，依赖 `SseEventPublisher` 并创建 `SseAgentEventSink`。L2 Registry 位于 core，却依赖 JPA Repository。Master 路由器包含日志、数据库、SRE 的关键词、业务编码和参数提取。

**判断：**当前“微内核 100% 零业务依赖”表述不成立，但这不意味着整个分层没有价值。确定性路由也不低级，只是不能被描述成已经实现通用模型自主规划。

**修复要求：**内核接受自己的请求模型与 `AgentEventSink`；SSE 适配层负责转换与组装；持久化通过端口提供；场景路由策略下沉到 scenario。内核可以保留必要的 Spring 集成，不必为追求形式纯洁而重写全部基础设施。

**验收：**替换为非 HTTP 接入不改内核；新增业务场景不改 core 的关键词分支；添加依赖边界测试，防止回归。

### F13｜逻辑过期没有约束实际内存占用

**定位：**[InMemoryCardRegistry][S04]、[InMemoryConversationMemory][S17]。

卡片到期后会拒绝提交，但 Map 没有相应的自动清理路径。会话记忆限制了单会话消息数，却没有限制会话总数、空闲存活时间及消息字节大小。持续新增会话和卡片仍可能导致内存持续增长。

**修复要求：**区分业务 TTL 与存储淘汰策略，设置容量、空闲过期、定期清理及指标；已结束卡片按保留期清理，进行中的写操作保留可追溯状态。真实审批和执行记录不能仅靠易失内存维持。

**验收：**通过可控时钟和容量测试证明过期对象会被清理；大量新会话不会无上限增长；清理任务不会破坏执行中的幂等记录。

### F14｜线程池隔离不等于完整的运行时治理

**定位：**[ThreadPoolConfig][S18]、[Pipeline.process()/executeRoute()][S01]、[两个 Agent 的流式处理][S02]、[S08][S08]。

使用专用、有界、命名线程池是正确基础。但 `CallerRunsPolicy` 在饱和时可能让请求调用线程执行长任务，Agent 又通过 `.blockLast()` 等待流结束。当前断连处理主要在收到 token 并发送失败时触发；如果上游长时间不再发 token，或者复合计划还有后续步骤，不能据此认定整个回合已经及时取消。

**修复要求：**补回合期限、模型调用期限、最大并发、队列准入、活动任务表和可传播的取消信号。保持阻塞式编排也可以，但必须承认其线程占用，不能只依据使用了 Flux 就认定全链路非阻塞。审计和执行记录不应放入允许静默丢弃的低优先级队列。

**验收：**慢模型有上限；队列饱和时返回明确拒绝或排队状态；断线取消后不启动下一步；线程、队列、拒绝、超时和取消有可观测指标。

### F15｜鉴权是生产前提，不应与 Demo 缺陷混淆

**定位：**[架构路线 2.2 的未完成项][S22]、[卡片入口][S05]、[FAQ 管理入口][S10]。

架构文档明确写出数据面与管理面尚未鉴权。它属于已知规划缺口；本报告没有验证实际部署是否另有网关控制，因此不声称线上服务一定对外裸露。

**发布要求：**在公网、多用户或真实敏感数据场景前，必须有可信身份来源、会话归属、管理角色、资源级访问控制、审计和速率限制。CORS 配置不是鉴权；随机会话 ID 也不是授权。日志、数据库查询等只读能力同样可能涉及敏感信息。

**验收：**匿名请求不能访问受保护接口；普通用户不能修改 Agent/规则/FAQ；跨用户会话及资源访问被拒绝；部署文档明确网关与应用各自承担的校验。

### F16｜文档状态漂移会继续制造错误实现

**定位：**[README][S21]、[07 架构路线][S22]、[00 工程规范][S23]、[03 协议文档][S26]。

README 仍描述旧的 GitHub Issue Demo、未接入的 Master 路由及规划中的记忆/卡片状态；`07` 的新状态矩阵与后续旧 GitHub 链路描述又互相冲突。协议文档中的卡片 TTL、服务端校验描述也需要与当前 15 分钟和已有部分后端校验对齐。

工程规范强调无外部依赖的默认实现，但没有足够明确地区分 Demo 与生产；这不应成为生产自动 Mock 的依据。文档及注释中出现的固定时延、全面就绪、零消耗等断言也需要绑定实际测量范围。L2 查询仍可能需要 Embedding，前置改写也可能调用模型，不能把检索本身的局部耗时当成整条请求成本。

**修复要求：**建立唯一能力状态表，每项绑定实现入口、测试和限制；其他文档引用该表。性能区分目标与实测，说明样本规模、向量维度、硬件和统计口径。文档中的“已实现”不自动升级为“生产可用”。

**验收：**README、架构与协议不再对同一功能给出矛盾状态；文档更新与相关代码/测试同批提交。

### F17｜现有测试需要补真实装配与异常链路

**定位：**[MultiTurnPipelineIntegrationTest][S19]、[L2VectorResolverTest][S31]、[SpringAiAgentApplicationTests][S32]、[前端 package.json][S25]。

现有测试有价值，但部分“集成测试”手动创建组件、使用直接执行器和 Mock ChatClientFactory，甚至显式创建无依赖 L2。这能验证受控逻辑，却不能证明真实 Spring 装配、线程执行及最终模型输入正确。前端构建脚本也不能代替 SSE 状态测试。

**修复要求：**增加容器装配测试、最终 Prompt 捕获测试、卡片权限与未知结果测试、HTTP/SSE 失败测试。离线 CI 使用可控假模型和假业务端口，真实外部系统联调独立设置，不应让测试执行真正的运维动作。

该基线没有返回 Actions 运行记录。本报告不提供“全部测试通过”的结论。

**验收：**第 8 节关键用例进入自动化；提交具备可追溯的构建、测试结果及明确的未覆盖范围。

### F18｜构建基线和数据库升级路径需要明确

**定位：**[pom.xml][S20]、[README][S21]、[sql/init_schema.sql][S24]。

README 要求 Java 21，而 POM 声明 `java.version=17`。POM 同时声明 Spring Boot `4.1.1`、Spring AI `2.0.1`，这些只是源码中的版本事实；本次未验证完整依赖解析和兼容性。仅凭 Java 文档差异，不能断言编译失败。

初始化 SQL 包含 `DROP TABLE IF EXISTS`。它可以用于明确的一次性 Demo 重建，但不能不加区分地作为已有数据环境的增量升级方式。

**修复要求：**统一开发、构建和 CI 的 Java 基线并固定工具链；在干净环境执行构建。把初始化/重置脚本与增量迁移分开，选择有版本记录的迁移机制；保留禁止 Hibernate 随意改表的意图，但不要把破坏性重建当作唯一升级手段。

**验收：**新环境可重复构建；已有数据升级不丢失记录；重置脚本用途和风险明确；迁移失败具备恢复方案。

## 6. 建议的架构收敛方向

### 6.1 先修依赖方向，再拆物理模块

建议的依赖方向如下，名称仅表示职责，不要求一次性新增全部类：

```text
web / SSE adapter
    └─ 应用请求、身份解析、接入协议、事件转换
         └─ core pipeline
              ├─ IntentResolver / Resolution
              ├─ SubAgent / StepResult
              ├─ ConversationMemory port
              ├─ CardRegistry / Approval policy
              └─ AgentEventSink

scenario
    └─ 业务路由策略、专家协同、诊断结果、操作草案
         └─ capability ports
              └─ infra / 外部系统 adapters

模型可用工具：查询、诊断、提案
真实执行入口：可信身份 + 服务端审批记录 + 参数校验 + 幂等执行
```

应保留已有的接口，不为命名统一而进行大面积重写。必要的新接口只为解决具体问题：输入缺失、结果传递、审批执行、可取消任务及基础设施替换。

### 6.2 三类数据不要混为一谈

| 数据 | 用途 | 约束 |
| --- | --- | --- |
| 原始输入与历史 | 保留用户真实表达、支持上下文 | 限制长度，敏感信息按策略处理 |
| 推理和检索的派生数据 | 路由、解释、诊断依据 | 不直接成为可信权限或执行命令 |
| 经确认的执行草案 | 对真实资源产生副作用 | 服务端签发、权限校验、不可变关键字段、幂等 |

模型给出的“操作人”“资源 ID”“已确认”等文本都属于派生内容，不能替代可信系统状态。

### 6.3 三类状态分别建模

连接状态、对话回合状态和外部操作状态不是同一件事。连接断开不等于外部操作失败；回合结束不等于卡片已经确认；回执失败不等于应再次执行。优先明确这些语义，再决定是否需要更多状态枚举或中间件。

### 6.4 Demo 与生产显式分离

Demo 可以提供 Mock 数据和内存实现，但应有可识别的模式标记。生产缺少关键执行依赖时明确失败，查询类能力可受控降级；降级结果不能冒充真实诊断或成功操作。测试依赖通过测试配置注入，不混进生产构造器。

## 7. 分阶段修复计划

以下按依赖与风险排序，不是时间承诺。每个阶段应拆成可独立审查的小提交，不把安全修复、全量重构和新功能混在同一个大改动中。

### 阶段 A：安全边界与真实装配

**处理问题：**F01、F02、F03，及 F05/F11 的最低安全约束。

交付：移除模型写工具；服务端绑定卡片类型、owner 与目标；显式构造注入；停止自动填充真实执行目标；端口失败不显示成功；增加容器及卡片安全回归测试。

**阶段门槛：**未经可信确认不能调用写端口；所有关键组件使用预期 Bean。真实 Ops 适配器仍保持禁用，直到阶段 D 的执行可靠性也完成。

### 阶段 B：上下文与 L2 数据链路

**处理问题：**F04、F06、F09 的模型输入相关部分。

交付：统一输入组装；明确原始/有效问题的双轨语义；历史与知识真正传入模型；Embedding 来源标记、异常策略及索引隔离；核实模型参数实际生效。

**阶段门槛：**最终 Prompt 断言通过；同维不同来源的向量被隔离；未知来源索引不参与生产直答。不要只因 L2 Resolver 能注入就直接打开检索流量。

### 阶段 C：回合协议与前端状态

**处理问题：**F07、F08、F10 的卡片展示部分。

交付：先修订 `03`；贯穿 turnId；确定首事件与 HTTP 响应竞态策略；按回合与 actionId 更新 UI；统一 HTTP 错误、连接就绪与终态。

**阶段门槛：**旧卡片回执不串消息；请求错误不会卡住页面；重复事件不重复应用；同会话并发策略明确。

### 阶段 D：真实操作、复合协作与运行保障

**处理问题：**F05、F10、F11、F13、F14、F15。

交付：结构化诊断结果及操作草案；步骤结果传递；持久化幂等和未知结果查询；身份与管理权限；任务超时、取消、准入；内存清理及关键指标。

**阶段门槛：**在受控测试环境证明外部副作用不因重试重复发生，匿名/越权请求被拒绝，取消不会继续启动后续步骤。完成后才讨论接入真实写能力。

### 阶段 E：文档、构建和迁移交付

**处理问题：**F16、F17、F18；并行补充前述阶段的 CI。

交付：一致的能力矩阵；更新 README 与协议；统一 Java/Node 构建基线；可复现的后端与前端检查；区分 SQL 重置与迁移；记录验收结果及限制。

**阶段门槛：**新的开发者按文档可在受控环境复现示例；不能因为某一步采用 Mock 就把整条生产链标为通过。

### 阶段 F：框架化交付

**处理问题：**F12 及长期交付目标。

交付：先通过依赖边界测试，再按需要拆 core、接入适配器、starter 和 sample；验证移除运维场景后仍能运行通用示例，新增第二种业务无需改 core。

**阶段门槛：**拆模块是对已稳定边界的表达，而不是用更多模块掩盖未完成的调用关系。

## 10. 发布边界与暂缓事项

### 10.1 受控 Demo

允许显式 Mock、单机内存和受限并发，但必须说明数据为模拟、状态不可持久恢复、不连接真实执行端口。即使是 Demo，也应先修复明显的装配和前端终态问题，避免教学内容与运行现象互相误导。

### 10.2 接入真实查询

在只读模式下也需要可信身份、资源范围、敏感数据处理、超时和日志策略。Embedding、检索知识、模型回答需保留来源及失败标识，不以模拟结果冒充真实查询。

### 10.3 接入真实写操作

必须满足：可信审批链、资源授权、不可变草案、服务端参数重建、执行幂等、未知结果查询、持久记录和审计。F01、F02、F05、F11、F15 未关闭前，不建议开启真实写能力。

### 10.4 多节点部署

本报告没有验证多节点能力。单机 SSE 连接表、内存卡片和记忆不能被当作天然可横向扩展。需要明确连接路由、共享状态、消息分发和恢复机制；仅添加粘性会话也不能替代持久化执行幂等与故障恢复。

### 10.5 暂缓投入

暂缓大规模模块拆分、通用 DAG 引擎、并行自治 Agent、更多业务插件和界面装饰性优化。先稳定一个完整场景：用户提出故障 → 查询证据 → 形成诊断 → 生成正确草案 → 人工核验 → 受控执行 → 返回可追踪结果。

**最终建议：现有结构值得继续，但下一轮的主题应是“把已经声明的功能真正接通并证明正确”，而不是继续增加抽象和功能数量。**
